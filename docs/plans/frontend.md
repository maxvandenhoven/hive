# Frontend

A single-page app in `frontend/`, built to static files and served by FastAPI. It must work
well on a phone at the table (camera, touch) and on a desktop (agent vs agent, replay).

## Stack

| Concern | Choice |
|---|---|
| Build | Vite + React + TypeScript (strict, `noUncheckedIndexedAccess`; 5.9, see `tooling.md`) |
| Package manager | npm (lockfile committed) |
| Styling | Tailwind CSS |
| Components | shadcn/ui (Radix base, `radix-nova` style, Lucide icons), copied into `frontend/src/components/ui/` and themed; app components build on them. Add primitives with `npx shadcn@latest add <name>` |
| Server state | TanStack Query |
| Routing | React Router |
| API types | `openapi-typescript` generated from FastAPI's OpenAPI schema (`hive openapi`, no server needed) into `frontend/src/api/schema.ts` by `make api-client`; `openapi-fetch` is the thin typed client, and `unwrap` turns error bodies into an `ApiRequestError` with the API error `code`. CI fails if the generated file is stale |
| Streaming | `fetch` + a small SSE reader for `POST /think` (`EventSource` only supports GET) |
| Lint/format/test | ESLint, Prettier, Vitest + Testing Library |

Dev: `vite` dev server proxies `/api` to uvicorn. Prod: `vite build` output is copied into
the image and mounted by FastAPI.

## Board rendering

Board logic is separate from drawing, so renderers are swappable (SVG now, a React Three
Fiber `ThreeBoard` later behind a settings toggle). Pages use a renderer only through its
props (`const Board: BoardRenderer = SvgBoard`):

```ts
interface BoardRendererProps {
  board: BoardView;              // stacks per hex, top piece first
  highlights: HexCoord[];        // where a click plays a move: targets or placements
  movable: HexCoord[];           // tiles that may move (ringed and raised)
  selected: HexCoord | null;
  lastMove: MoveView | null;     // from (null for a placement) and to
  proposedMove: MoveView | null; // an agent's best move, the move to make on the table, a hint
  forbidden?: HexCoord[];        // "not allowed" hexes for the rule diagrams; games omit it
  diagram?: boolean;             // a help diagram, without the key and zoom buttons
  onHexClick: (coord: HexCoord) => void;
}
```

`proposedMove` carries every move an agent suggests: its best move while it thinks, a
pending move to make on the table and a hint (WP 35). They share one mark and one colour
(`--board-suggestion`), and at most one is shown at a time (hints only on a person's
turn, the others only on an agent's), so renderers need no kind; the turn prompt says
which it is. While one is shown, the "can move" marks are hidden on the board and in the
hand trays, so the suggestion's rings are the only rings; tapping still works.

Renderers know nothing about the game: every hex reports clicks, also empty ones, and the
interaction code decides what a click means. Showing the contents of a stack is part of
drawing, so the renderer owns it: tapping a stack of two or more pieces that is not a
highlight opens a popover listing its pieces from the top; tapping it again, or anywhere
else, closes it. While a mouse pointer is near the popover it fades out and lets clicks
through, so the tiles below it stay reachable.

`useBoardInteraction` owns the selection and maps clicks to intents (`resolveHexClick`,
`resolveHandClick`, pure and tested on their own): select a movable tile → fetch its
targets (`GET /targets`) → click a target → play the move. Selecting a piece type in the
`HandTray` highlights `placeable_coords` instead. Clicking the selection again, or a hex
that is neither movable nor highlighted, clears it. A highlight wins over a movable tile
on the same hex (a beetle climbing onto it). With a hint shown and nothing selected,
tapping the hint's target selects the hinted piece, like tapping the piece itself, so
following a hint takes two taps. Moves are only built from the API's targets
and placements, so only legal moves are sent. The selection belongs to a ply and is
dropped when the position changes or the board is disabled (agent turn, game over, a move
being sent).

`SvgBoard` draws a background hex grid (`--board-grid` on `--board-surface`), then tiles
(owner colours, the insect graphic, the pieces below the top one peeking out, a stack
height badge) and the marks, all in the board colours of [Theme](#theme). The grid is one
path of the hexes that overlap the visible part of the board (`gridCells` in `grid.ts`),
recomputed from the `viewBox` and the SVG's measured size (`visibleViewBox`, since a
`meet` viewBox shows more along the longer side), with a non-scaling 1.25 px stroke so it
reads at every zoom level.

**Marks.** One mark per meaning (`marks.tsx`, kinds in `boardMarks.ts`), each also told
apart by shape, dash or fill so it reads without colour:

| Mark | Prop | Drawing |
|---|---|---|
| Can move | `movable` | Solid ring on the tile, which is raised by a shadow (`--board-movable`) |
| Selected | `selected` | Narrow unfilled outline around the rounded tile (`--board-movable`) |
| Can go here | `highlights`, empty hex | Dashed hex with a dot (`--board-target`) |
| Can climb on top | `highlights`, occupied hex | Dashed ring with a dot on the tile (`--board-target`) |
| Last move | `lastMove` | Dotted outline with a light fill on from, stronger on to (`--board-last-move`) |
| Agent suggestion | `proposedMove` | Rounded ring around the piece to move (on the board, or in the hand tray for a placement), an arrow, and a rounded double ring on the target, all inside the hex with a gap around the tile (`--board-suggestion`) |
| Not allowed | `forbidden` | Hex with a cross (`--board-forbidden`), for the rule diagrams of WP 38 |

The hand trays use the same components: a placeable piece is raised with a ring, the
selected one has an unfilled outline.

**Legend.** `BoardLegend` is a Key button with a small panel that lists the marks on the
board now first (`boardMarksShown(props)`), then the rest, each with a swatch drawn by
`MarkSwatch` from the mark components themselves, so they always match. Whether it is
open is remembered per device (`localStorage`). A renderer places it on the board (the 2D
board at the bottom left); the 2.5D board (WP 39) and the help (WP 37) reuse it and
`MarkSwatch`. On a phone the panel leaves out the one-line descriptions.

Interactive parts are SVG elements with `role="button"` and keyboard activation. The view
is the SVG `viewBox` in board units, so fitting needs no measuring: it fits the stacks plus every neighbouring hex (where all
targets lie, so the view stays steady while selecting), with a minimum size. Dragging pans
(after a 6 px threshold, so taps stay clicks), two pointers pinch to zoom, the mouse wheel
and the buttons zoom; the view then stays put until the fit button. The SVG has
`touch-action: none`, so the page does not scroll or zoom while panning the board.

The insect graphics are imported from `src/hive/assets/svg/` through the `@insects` Vite
alias (`server.fs.allow` admits the folder in dev), so the Python plots and the app share
one copy. The frontend build therefore needs that folder next to `frontend/`, including in
the Docker build stage (WP 25).

## Theme

One theme, "Slate & Honey" (D28): cool slate neutrals, a dark slate header and one honey
accent. No dark mode and no theme switch, so `ui/` has no `dark:` classes and there is no
`next-themes`. It should feel calm and a bit premium: no illustrations, no bouncy UI.

The tokens live in `frontend/src/index.css` as CSS variables, exposed as Tailwind colours
(`bg-card`, `ring-board-movable`, `fill-tile-white`). App components style only through
these tokens and the `ui/` variants, never with one-off colours. Values were adjusted from
the mockup where WCAG AA needed it (marked *).

| Token | Value | Use |
|---|---|---|
| `--background` | `#e8ecf0` | Page |
| `--foreground` | `#1c2530` | Text (13:1 on the page) |
| `--muted-foreground` | `#536070`* | Secondary text (≥ 4.5:1 on page, card and secondary) |
| `--card`, `--popover` | `#f7f9fb` | Cards (`--border` ring and a faint shadow), popovers |
| `--border` | `#d3dae1` | Card and table borders |
| `--input` | `#7b8896`* | Input, select and checkbox borders (3:1 on the page) |
| `--secondary`, `--muted`, `--accent` | `#dfe5eb` | Secondary buttons, finished badges, hovers |
| `--primary` / `--primary-foreground` | `#e0a526` / `#1c2530` | Primary buttons, active and "your turn" badges, the hand of the side to move |
| `--ring` | `#a8740c`* | Focus rings: a deeper honey, ≥ 3:1 on page and card |
| `--destructive` | `#b42828`* | Errors and delete actions (5:1 on the page) |
| `--header` / `--header-foreground` | `#1c2530` / `#f3f5f7` | App header with the honey hexagon logo |

Honey is for fills, never for text on light surfaces (2:1). Links are foreground text with
a honey underline. Status badges: active is primary (honey), finished secondary, abandoned
outline. In the game list the next action badge is primary when the game waits for a
person (*Your turn*, *Agent's move to make*), secondary for an agent's turn or a result,
and outline once abandoned.

**Board colours.** Each board colour has one meaning, shared by the 2D board, the 2.5D
board (WP 39), the legend (WP 32) and the help. CSS can use the classes; renderers that
cannot (Three.js) read the same values from `components/board/colors.ts`, which a test
keeps equal to `index.css`. The Python plots keep their own colours.

| Token | Value | Meaning |
|---|---|---|
| `--board-surface` | `#d5dde5` | The board background (the board card) |
| `--board-grid` | `rgb(28 37 48 / 16%)` | The background hex grid (WP 32) |
| `--tile-white` / `--tile-black` / `--tile-stroke` | `#f6f1e6` / `#2a2f36` / `#4a5562` | Tiles of each side and their outline |

| `--board-forbidden` | `#d64545` | "Not allowed" in rule diagrams |
| `--board-last-move` | `#e0a526` | The last move |
| `--board-suggestion` | `#8b5cf6` | A move suggested by an agent: its best move while thinking, the move to make on the table, a hint |

The stack height badge is neutral (card fill, foreground text), since a stack has no
board meaning of its own.

**Frame.** The header and the page share one frame: up to 96 rem wide on a desktop, one
column with 16 px gutters on a phone. The right of the header is kept for actions, now
the **Help** button.

## Flows

**Games page (WP 13, WP 34).** List games, paged by `?page=N`; open, rename, export and
delete from a row menu. Each row shows the name with the scenario under it (an icon and
*vs agent*, *hints game* or *watching*), the next action rather than only the status
(*Your turn*, *Sam to move* for the opponent in a hints game, *Agent's
move to make* for a pending move, *nm3 to move*, *White won*), the players (wide screens),
the ply and when it changed. `lib/players.ts` derives both from the `GameSummary`
(`gameScenario`, `describeGameScenario`, `describeNextAction`), without loading moves.

**New game (WP 34).** A flow that asks what the person wants to do instead of a player
type per side (D26). On a phone it is a full-screen sheet, on a desktop a dialog; both
have a back button from the setup to the scenarios.

1. *Choose a scenario*: three large cards with an icon and one sentence: *Play against an
   agent*, *Play a friend with hints*, *Watch two agents*.
2. *Set it up*:
   - Against an agent: your colour (white, black or random, drawn when the game starts),
     the opponent, and hints for yourself (off by default) with a hint strength. Always
     on the screen.
   - A friend with hints: your colour, the opponent's name (default *Opponent*) and the
     hint strength. Only you get hints. Always at the table.
   - Watch two agents: the white and the black agent. Always on the screen.
   - An optional name, defaulting from the scenario (`You vs nm3`, `You vs Sam`,
     `nm3 vs nm2`).

Agents are picked by `AgentChoiceField` from `GET /agents/presets` as named strengths with
the default budget (5 s); **Advanced…** opens `AgentPicker` (kind, params, label and
budget), starting from the chosen preset. The first game defaults to the strongest preset
(the last by name) against the person, and the strongest against the weakest when
watching. Without presets the choice starts in Advanced with the first kind.
`lib/newGame.ts` holds the choices of all three scenarios (so switching keeps them),
builds the `GameCreate` request (players, hint agents and `board_location`) and remembers
the choices per device (`localStorage`, checked field by field against the agents now
offered) once a game is created. With remembered choices the flow opens at the setup of
the last scenario, so a similar game takes two taps (New game, Start game). The new game
opens once created.

The param form (`lib/agentParams.ts`) supports integers, numbers, booleans, strings and
string enums, each optionally nullable (an empty input is `null`); other schemas are edited
as JSON. Inputs hold drafts that are checked live against the schema bounds, and params left
at their default are not sent, so specs keep following the agent defaults.

**Game page (WP 14, WP 35).** Header (name, status, players, whose turn and the ply),
the turn prompt, the board between the two hand trays, undo, export and the move list.
The side of the person using the app (`ownSide`: the human side against an agent, the
unnamed side in a hints game) is drawn at the bottom; otherwise white is. Turns and
results name the sides as *You*, the opponent's name or the agent (`sideName`). On a phone the parts stack in one column with a square board; on a desktop the
header, the thinking panel, actions and moves sit in a side panel. Manual entry by
tapping as described under "Board rendering". Moves are sent with `expected_ply` set to
the `ply_count` of the position shown and undo with `?expected_ply=`, so a stale page
cannot overwrite a newer game: the 409 is shown as a toast and the game is refetched. A
move, undo, confirmation or committed agent decision stores the returned position as the
latest, drops cached targets and stored positions from that ply on, and refreshes the
game and the game list. In a human vs agent game, undo takes back to the person's last
turn (two moves when the agent answered, also when its answer is still pending, so the
person takes both back on the table), so the agent does not replay its answer at once;
several plies are undone in one mutation. Abandoned games are read-only.

Query notes: positions (`["games", "detail", id, "position", ply | "latest"]`) and targets
live under the game's key, so refreshing a game refreshes them. Queries whose `meta` sets
`toastErrors` report failures in a toast like mutations (used for targets, which follow a
click). openapi-fetch reads tuples such as `Coordinate` as plain arrays, so responses with
coordinates are cast to their schema types in `queries.ts`.

**Turn prompt (WP 35).** `TurnPrompt` is a strip above the board with one sentence on
what to do now and only the actions that fit (`describeTurnPrompt` in `lib/turnPrompt.ts`
picks the sentence from the scenario, the board location and the state):

| State | On screen | At the table |
|---|---|---|
| Your turn | *Your turn: tap a piece on the board or in your hand* | Only older games against an agent |
| Hints game | – | *Your turn* or *Sam's turn: make the move on the table and enter it*, **Hint** on your turn |
| No legal move | *Your turn: no move is possible, so pass* with **Pass** | Same |
| Agent thinking | *nm3 is thinking…*, with the thinking panel | Same |
| Agent failed | *nm3 could not move* with **Try again** | Same |
| Agent decided | The move is applied and play continues | *Make this move on the table: ant moves next to the white queen* with **Done** |
| Watching | *Watching nm3 vs nm2* with the match controls | – |
| Game over | *You won after 23 moves* (*nm3 won*, *White won*, *Draw*) with **Undo** and **New game** | Same |
| Abandoned | *This game was abandoned* with **New game** | Same |
| Replay | *Showing the position after move 7: go live to play on* with **Go live** | Same |

A pending move comes before the result, since an agent's last move can be pending. Moves
are described by the pieces they touch (`describeMoveOnBoard` in `lib/moves.ts`): *place
spider next to the black queen*, *ant moves next to the white queen and the black
beetle*, *beetle climbs onto the black queen*, *beetle climbs down next to …*,
*grasshopper jumps over the white queen*; a piece with a twin of the same kind and owner
is told apart by where it stands (*ant beside the black spider moves …*, or its
coordinate as a last resort). These read the same from any side of a table and in any
rotation of the 2.5D board. The move list keeps coordinates.

**Hints (WP 35).** On the turn of a side with a hint agent, a **Hint** button sits in the
prompt and on that side's hand tray. `useHint` keeps hints hidden until asked for, then
starts `POST /think` with `commit=false`, which uses the side's hint agent and budget. The
prompt shows a compact indicator with the time left, then the move as a sentence (*Hint:
grasshopper jumps over the white queen*) and the board draws it as `proposedMove`.
Pressing **Hint** again hides it (asking once more shows the same hint without thinking
again; a failed hint is asked for again). Tapping the hinted piece, or the hint's target,
selects the piece, so following a hint takes two taps. A hint belongs to one position:
any move or undo clears it. Hiding it, a move or leaving the page aborts a search under
way. Hints are never applied by themselves.

**Game page, agent turn (WP 15, WP 35).** `useAgentTurns` starts `POST /think` with
`commit=true` whenever an agent is to move in an active game and no other write is under
way. `api/sse.ts` reads the stream from `fetch` (`EventSource` only supports GET):
`ServerSentEventParser` turns chunks into event data, `streamThinkEvents` yields the typed
events and throws an `ApiRequestError` for an error response. The `ThinkingPanel` shows
the time left of the side's budget (counted from when the stream opened), depth, score
(`Win in 3 plies` for forced results), nodes and nodes/s, and the best move so far, which
the board draws as `proposedMove` (an arrow from its source and a double ring on its
target). When the decision arrives with its position, the move is stored. On the screen
play continues at once (WP 36 animates the move in). At the table the API stores the move
as pending (D27): the prompt asks to make it on the table with **Done**, the board keeps
pointing at it, and the person cannot play until Done calls
`POST /moves/last/confirm`. Both follow `pending_move` of the stored position, so the
prompt is the same after a reload or when coming back from the game list. A failed
request or an `error` event (for example `ply_conflict`) is shown as a toast, in the panel
and the prompt with **Try again**, and the game is refetched. The stream is aborted, which
stops the agent without committing, when the page closes, another write starts (undo
while the agent thinks) or a match pauses.

**Agent vs agent (WP 15).** `MatchControls`, in the turn prompt: **Play**/**Pause**,
**Step** (one move while paused) and a delay between moves (none, 1, 2 or 5 s, default
1 s). The page drives the loop by calling `think` with `commit=true` for whichever side is
to move, and the thinking panel shows the search and then the move just played. Matches
do not wait for Done, since they are watched on the screen; Step plays one move at a time
for following on a physical board. A match starts paused, and undo pauses it.

**Replay (WP 15).** `ReplayControls` (first, previous, next, live and a slider) and the
move list (a move shows the position after it) set the ply shown, loaded with
`GET /state?ply=N`; the position shown before stays while the next one loads. The last ply
is the live position, which follows new moves; a replayed ply past the last move (after
an undo) shows the live one. Replayed positions are read-only and marked on the board,
while agent turns carry on in the live game.

**Camera (WP 16, WP 19).** A camera button on human turns opens `CameraCapture`
(`<input type="file" accept="image/*" capture="environment">` first; a `getUserMedia`
viewfinder with a framing overlay later). WP 16 uploads and stores the photo. WP 19 shows
the proposed move for confirmation, or `MatchCandidates` (top candidates plus manual entry)
when the match is weak. On agent turns, the photo verifies that the expected move was
made. Camera access needs HTTPS, which the Tailscale ingress provides in production; in
local dev use `localhost`.

## Help

**Help page (WP 37).** `/help`, opened by **Help** in the header, has one section per
topic, each with an anchor that help links point to (`lib/help.ts` lists the ids, and a
test checks that the page has each one).

| Anchor | Covers |
|---|---|
| `scenarios` | The three scenarios, on the screen versus at the table, and hints |
| `board` | The legend with every description (`BoardMarkList`), and small diagrams of the marks in play |
| `controls` | Selecting and playing, the hand trays, pass, undo and how many moves it takes back, replay and the move list, pan, zoom and fit, stack contents, the Tips button |
| `games` | Each label of the game list |
| `leaving` | What is kept when the page closes (moves, a pending move until Done, paused matches) and what is not (a thinking agent's search, hints, the replay position) |
| `rules` | A link to the rules reference |

Content lives in TSX next to what it explains (`components/help/`, and the help texts
of the game page in `lib/gameHelp.ts`). Diagrams are `BoardDiagram`, the real renderer
with `diagram` set (no key, no zoom buttons) on fixture positions, with a caption. A
diagram with steps has previous and next buttons, and each step marks the step just made
as the last move. Board animations (WP 36) were dropped, so the help does not mention
them and diagrams step instead of animating.

**Help buttons.** `HelpButton` is an info icon with a popover that holds a title, a short
answer and *More in the help*, linking to a section. One sits next to the game list heading
(statuses), one in each step of the new game flow (the scenarios, then per setup where it
is played and hints), and one in the turn prompt, with the help for the current scenario
and turn (`describeGameHelp`, by the prompt kind).

**Board tips.** `boardTips` picks dismissible tips for the scenario and state, for example
*Tap a piece with a blue ring to see where it can go*, *Press Hint for a suggestion* and
*Make the agent's move on the table, then press Done*. The placement tip, and the tip when
only the queen may be placed on the fourth turn, link to the rule. Tips show in the first
three games of each scenario on a device until the **Tips** button in the game actions is
pressed, after which the choice holds on that device (`lib/tips.ts`, `localStorage`).
Dismissed tips stay dismissed.

**Rules reference (WP 38).** `/help/rules` has one section per rule of the base game,
namely pieces and goal, turns and placement, one hive, freedom to move, each insect, passing and
the end. Repetition draws get a section once WP 30 adds them to the engine. Each section
has at least one `RulesDiagram`, with allowed targets in `--board-target`, forbidden
ones crossed out in `--board-forbidden`, the moving piece selected, and steps along its path
where motion explains the rule (the queen's step, the beetle's climb, the grasshopper's
jump, the spider's three steps).

The diagrams are checked against the engine. `scripts/rules_diagrams.py` defines each
position in a compact notation (`"bA wB"` is a white beetle on a black ant) with the
piece that moves, the forbidden targets chosen by hand and the path. It computes the
allowed targets from `Rules.legal_moves`, fails when a forbidden target is legal or a path
does not lead to an allowed target, and writes `components/help/rulesDiagrams.json`
(`make rules-diagrams`). A pytest fails when the committed file is stale, like
`make api-client`, and a vitest renders every diagram.
